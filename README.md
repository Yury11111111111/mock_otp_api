# Mock OTP Bank — POS / BNPL API + Webhooks

Мок-сервер, эмулирующий API и вебхуки ОТП Банка (POS-кредитование «Смарт-анкета»
и BNPL «Давай делить») для тестирования обработки заявок на вашей стороне.
Все данные моковые — сервер ничего не отправляет в реальный банк.

Бэкенд — Node.js/Express. Фронтенд — React (подключается через CDN прямо
в браузере, без сборки, см. `public/index.html` и `public/app.jsx`).

## Что внутри

- Мок OAuth2/Keycloak авторизации (`grant_type=password` с авторегистрацией,
  `grant_type=refresh_token`)
- Мок POS API: `GET /broker/core/api/v1/states...`
- Мок BNPL API: `POST/GET /pos-bnpl-partner-api/api/v1/applications...`,
  `cancel`, `commit`, `refund`
- Отправитель вебхуков в форматах POS и BNPL (с повторными попытками при
  ответе не 200), настройки — свои у каждого пользователя
- React-панель: создание и **редактирование** моковых заявок, ручная смена
  статуса → автоматическая отправка вебхука, просмотр логов входящих
  запросов и отправленных вебхуков, инструкция прямо на экране входа

## Запуск локально

```bash
npm install
cp .env.example .env   # при желании поменяйте JWT_SECRET
npm start
```

Откройте `http://localhost:3000` — попадёте на экран входа с инструкцией.
Введите любой логин/пароль — аккаунт создастся автоматически.

## Как пользоваться

1. Откройте сайт → введите логин/пароль (создастся тех.учётка).
2. Вкладка **Настройки** → укажите URL вашего реального webhook-приёмника
   отдельно для POS и для BNPL. Ниже — готовый список адресов мок-API,
   которые нужно указать в вашей системе вместо `https://ecom.otpbank.ru/...`
   и `https://poslogin.otpbank.ru/...`.
3. Вкладки **POS заявки** / **BNPL заявки**:
   - «+ Создать заявку» — создаёт моковую заявку с дефолтными данными;
   - «Редактировать» — правит клиента, сумму, товар, точку продаж и т.п.
     без пересоздания заявки;
   - выберите статус в выпадающем списке и нажмите «Сменить статус + вебхук» —
     сервер отправит POST на настроенный webhook URL с телом в формате банка.
4. Вкладка **Логи** — все входящие запросы к мок-API и результаты отправки
   вебхуков (код ответа, тело, ошибки, номер попытки).
5. Кнопка «Показать Bearer token» в шапке — скопировать текущий токен для
   использования в Insomnia/Postman при ручных запросах к мок-API.

## Как проверить приём вебхуков (кратко; подробно — на экране входа сайта)

Мок сам делает исходящий POST на URL из настроек. Чтобы проверить, что
**ваш** обработчик правильно его принимает:

1. **Быстрый просмотр без кода** — создайте временный URL на
   [webhook.site](https://webhook.site), вставьте его в настройки, смотрите
   входящие запросы прямо в браузере. Хорошо, чтобы один раз увидеть
   структуру payload, но не тестирует вашу реальную бизнес-логику.
2. **Ваш обработчик локально (localhost)** — пробросьте его наружу через
   [ngrok](https://ngrok.com) (`ngrok http 4000`) или Cloudflare Tunnel,
   полученный публичный https-адрес укажите как webhook URL в настройках.
3. **Ваш обработчик уже задеплоен** — просто впишите его публичный URL,
   ничего дополнительно поднимать не нужно.

Требования к обработчику:
- Принимать `POST` с `Content-Type: application/json`.
- Обязательно отвечать `HTTP 200` — иначе (как и настоящий банк) мок
  повторит отправку (число повторов и задержка между ними настраиваются
  в разделе «Настройки»).
- Обновлять состояние заявки по полю `state`/`status` из тела запроса
  (см. форматы ниже).

Для точечной проверки без похода через мок можно также постучаться в свой
обработчик напрямую curl'ом с готовым примером payload — это быстрее, чем
каждый раз создавать заявку и менять статус через интерфейс.

## Переменные окружения

```dotenv
PORT=3000
JWT_SECRET=change_me_to_a_random_string
```

`JWT_SECRET` — просто секрет для подписи выданных токенов, пользователю
нигде не показывается и не настраивается через интерфейс. Отдельного
`ADMIN_PASSWORD` больше нет — доступ определяется исключительно
логином/паролем тех.учётки, который каждый пользователь задаёт себе сам.

## Ограничения мока
- Мок не валидирует бизнес-правила банка (лимиты, скоринг и т.п.) — он лишь
  воспроизводит структуру запросов/ответов/вебхуков для проверки вашей
  интеграции.
- Разделение данных между пользователями логическое (по полю `owner` в
  общем JSON-файле), а не физическое — этого достаточно для тестового
  инструмента, но не подходит как модель безопасности для чего-то большего.
